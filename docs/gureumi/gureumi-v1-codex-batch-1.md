# Codex 작업 지시 — 구르미 v1.0 공개 전환 / 1차 배치

온기 저장소의 구르미 테스트를 정식 공개하기 위한 첫 번째 변경 배치를 진행해줘.
이번 범위는 **공개 Beta 문구 정리 + 결과 화면 인라인 공감도 + 해당 변경의 회귀 테스트 + 최소 문서 갱신**이다.

새로운 검사를 만드는 작업이나 전체 서비스 리팩터링이 아니다.

## 0. 작업 원칙

- 먼저 현재 branch, git status, 관련 diff를 확인하고 사용자 변경을 보존한다.
- 필요하면 `feature/gureumi-v1-release` 브랜치를 사용한다. 이름이 이미 있거나 현재 작업이 섞여 있으면 파괴적인 전환을 하지 않는다.
- commit, push, merge, deploy를 하지 않는다. 운영 DB·secret·환경변수를 변경하지 않는다.
- 새 패키지 설치, 일괄 의존성 업데이트, DB schema 개편은 하지 않는다.
- 실제 로컬 코드가 아래 사전 확인 내용과 다르면 로컬 코드를 확인하고 차이를 보고한다.
- 운영 서버에 테스트 attempt나 피드백을 대량 생성하지 않는다. 자동화 검증은 로컬/테스트 DB에서 한다.

## 1. 사전 확인된 내용

2026-09-14 GitHub 기본 브랜치 읽기 기준이며, 테스트 실행 결과는 아니다.

- `GureumiService`는 27문항·축별 9문항 검증, 서버 채점, 완료 중복 시 기존 결과 반환, 완료 이후 답변 변경 차단을 구현한다.
- `GureumiScoring`: 9~22 LOW, 23~36 HIGH, 21~24 near-boundary.
- `GureumiScoringTest`에 정/역채점과 8유형 매핑 테스트가 있다.
- 기존 E2E에 답변/결과 복원·피드백·재검사 흐름이 있다.
- 소개·결과·피드백·공유 메타데이터·README에 Beta 문구가 남아 있다.
- 결과의 공감도 입력은 별도 피드백 화면에 있다.
- `GureumiService.saveFeedback()`은 quick 피드백 필드를 함께 갱신한다. rating 단독 저장 시 다른 의견이 초기화되지 않도록 주의해야 한다.

### 유지할 제품 규칙

- 문항 문구·선택지·순서·축·highSide·점수·cutoff·near-boundary·8유형 매핑을 바꾸지 않는다.
- 찌릿이 0건 또는 걱정 HIGH 70.6%를 이유로 분포를 조정하지 않는다.
- 완료된 결과와 진행 중 attempt의 검사 버전을 유지한다.
- 문항/채점 변경이 없으므로 내부 `GUREUMI_BETA_V01`, version_id, 적용된 migration을 바꾸지 않는다.
- 공개 v1.0 전환을 이유로 온기 전체 package 버전을 1.0.0으로 바꾸지 않는다.
- 내부 URL `gureumi-beta-stats`와 기존 공개 공유 URL의 호환성을 유지한다.
- 프론트에는 문항별 axis, highSide, score, cutoff 같은 채점 메타데이터를 추가하지 않는다.
- 공개 캐릭터 소개까지 숨기거나 개발자도구 차단/난독화로 보안을 대신하지 않는다.

## 3. 공개 문구 정리

공개 구르미 소개, 결과 피드백 영역, 상세 의견 화면, 홈 카드, README, 공유 메타데이터에서 현재 노출되는 Beta/BETA 1/v0.1 표현을 정리한다.

문구 기준:

- 콘텐츠 이름: `구르미 테스트`
- 소개 제목: `나는 어떤 구르미일까?`
- 소개: `27개의 선택을 따라가며 나와 닮은 구르미를 만나보세요.`
- 시작 버튼: `테스트 시작하기`
- 문항 수: `27문항`
- 공유 설명: `27개의 선택으로 만나는 나의 구르미. 서로 다른 반응을 가볍게 알아보세요.`
- 공유 CTA: `테스트하러 가기`
- 고지: `놀이형 자기이해 콘텐츠이며, 정식 TCI 검사나 심리 진단이 아닙니다.`

실측 근거를 찾지 못하면 기존 `약 4~5분`은 빼고, 다른 소요시간을 추정해서 넣지 않는다.
기존 이론 참고 설명, 문항·이미지·폰트의 출처/권리 표기, 제작자 크레딧은 보존한다.

공개 배너를 새로 크게 만들거나 모든 화면에 v1.0 배지를 붙이지 않는다. 기존 디자인을 유지한다.
README에서 구르미를 이미 이용 가능한 콘텐츠로 소개하되 과거 Beta 검증 기록을 삭제하지 않는다.

내부 검사 코드, enum, API 경로, 과거 문서 기록에 대한 전체 문자열 치환은 금지한다.
정적 이미지 안의 Beta 문구가 발견되면 기존 이미지 생성 소스와 절차가 있는지 확인한다. 해당 자산만 안전하게 수정할 수 없으면 남은 작업으로 정확히 보고하고 임의로 새 이미지를 만들거나 폰트를 바꾸지 않는다.

## 4. 결과 화면 인라인 공감도

현재 결과 화면에서 별도 페이지로 이동하지 않고 공감도만 바로 저장할 수 있게 한다.

### UI

- 핵심 결과 설명 뒤, 하단 공유 행동 전에 작은 영역으로 배치한다.
- 질문: `결과가 나와 얼마나 비슷했나요?`
- 1: `전혀 비슷하지 않아요`
- 2: `별로 비슷하지 않아요`
- 3: `조금 비슷해요`
- 4: `많이 비슷해요`
- 기존 구르미 UI의 색상·간격·Typography·라디오 스타일을 재사용한다.
- 기본값은 무선택이다. 저장된 공감도가 있다면 그것만 복원한다.
- 선택 시 즉시 저장하며 별도 제출 버튼/설문 화면으로 이동하지 않는다.
- 키보드 선택, 명확한 radio label, 모바일 터치, 저장 상태 안내를 지원한다.
- 강제 모달, 결과를 가리는 배너, 신규 홍보 문구를 추가하지 않는다.

### 저장과 실패 처리

- 현재 완료 attempt와 resume token으로만 저장한다.
- 1~4 외 값 및 미완료 attempt, 타인 attempt의 저장은 서버에서 거부한다.
- 같은 attempt의 공감도를 수정하면 같은 기록이 갱신된다.
- 실패 시 성공 메시지를 띄우지 않는다. 미저장 상태를 알려주고 재시도를 제공한다.
- 빠른 연속 입력에 대해 요청을 직렬화하거나 저장 중 입력을 잠그는 등, 늦은 응답이 최신 선택을 덮어쓰지 않게 한다.
- 새로고침 및 결과 재방문 시 기존 저장값을 복원한다.
- 응답하지 않아도 공유·이미지 저장·재검사·홈 이동을 사용할 수 있어야 한다.

### 기존 피드백 보존 — 필수

rating 단독 갱신으로 아래 값이 초기화되면 안 된다.

- confusingQuestionOrders
- selfSelectedResultType
- 기존 후속 설문 필드와 자유의견

기존 API 계약으로 안전하게 처리할 수 있으면 재사용한다. 누락값의 의미를 바꿔 기존 호출을 깨뜨리지 않는다.
전체 덮어쓰기 위험을 피하려면 rating만 갱신하는 작은 서비스 메서드와 전용 API를 추가해도 된다. 이 경우 기존 endpoint를 유지하고 DTO·인가·테스트를 포함한다. schema migration 없이 가능한 범위를 우선한다.

반대 방향도 확인한다. 상세 의견 화면을 열어 다른 항목만 저장했다고 기존 인라인 공감도가 null로 지워지면 안 된다. 기존 값을 불러오거나 각 저장 경로가 자기 필드만 갱신하도록 명확히 처리한다.

상세 피드백·후속 설문은 `자세한 의견 남기기`로 계속 제공한다. 상세 설문 삭제나 새 설문 문항 추가는 하지 않는다.

## 5. 통계 호환성

- 기존 관리자 통계 구조를 재사용한다.
- rating 없는 기록은 공감도 평균/분포의 유효 응답 수에서 제외한다.
- 인라인 rating 기록은 기존 공감도 통계에 1회 반영된다.
- 상세 의견만 남긴 기록을 기본 점수나 0점으로 채우지 않는다.
- 공감도 응답률은 해당 cohort의 실제 rating 응답 수 / 완료 수로 계산한다.
- 기존 `feedback submitted` 지표가 전체 피드백 존재를 뜻한다면 그 의미를 무단 변경하지 않는다. 공감도 응답 건수와 구분한다.
- 통계가 이미 이 기준을 만족하면 수정하지 않는다.

## 6. 회귀 테스트

기존 테스트를 먼저 재사용하고 이번 변경에 필요한 사례만 추가한다.

최소 확인:

1. 공개 시작 CTA와 주요 구르미 화면의 정식 문구.
2. 결과 화면 공감도 무선택 초기 상태와 기존 값 복원.
3. 1~4 저장, 같은 attempt 재입력의 갱신, 새로고침 후 유지.
4. 저장 실패·재시도 및 연속 입력 처리.
5. 인라인 공감도 저장 후 기존 상세 의견/후속 설문 유지.
6. 상세 의견 저장 후 기존 인라인 공감도 유지.
7. 공감도 미응답이어도 재검사와 공유 UI 이용 가능.
8. 잘못된 rating, 미완료 attempt, 다른 resume token의 저장 거부.
9. 기존 27문항 완료·이어하기·결과 복원·재검사 E2E 유지.
10. 기존 정/역채점·경계·8유형 테스트 유지.

mock 기반 테스트, 실제 backend 연동 테스트, 실제 모바일/카카오톡 확인을 구분해서 보고한다.
현재 E2E fixture의 외부 네트워크 차단을 풀어 카카오톡 실사용을 자동 통과처럼 만들지 않는다.

확인된 검증 명령은 아래와 같으며 로컬 최신 scripts와 설정을 먼저 확인한다.

```bash
npm run typecheck
npm run verify
npm run test:e2e -- e2e/gureumi.spec.ts
(cd backend && ./gradlew test)
```

Playwright와 Testcontainers의 실행 조건을 확인한다. Docker/JDK/브라우저 등 환경이 없어 실행하지 못한 검증은 정확히 미실행으로 보고한다.
현재 package.json에는 lint script가 확인되지 않았다. 로컬에 없다면 검증을 했다고 주장하거나 이번 작업만을 위해 lint 체계를 새로 만들지 않는다.
실패가 기존 문제인지 이번 변경인지 구분한다. 테스트를 통과시키기 위해 assertion을 삭제하거나 의미를 약화하지 않는다.

## 7. 최소 문서와 완료 보고

`docs/gureumi/release-v1.md`를 작성한다.

필수 기록:

- 이번 공개 전환 범위와 변경한 파일
- 공개 버전과 내부 검사 버전이 다른 이유
- 문항·채점·기존 결과를 변경하지 않았다는 확인 근거
- 인라인 공감도와 기존 상세 피드백의 저장 계약
- 실제 실행한 명령과 결과, 미실행 검증
- 실제 모바일·카카오톡·운영 설정 등 사용자가 확인해야 할 항목
- backend API 추가 시 호환 배포 순서 및 rollback 주의점
- 아직 배포/정식 공개하지 않았다는 상태

최종 응답에는 다음만 정리한다.

1. branch 및 변경 파일 요약
2. 구현한 동작과 중요한 설계 선택
3. 데이터·API·UI 호환성 확인
4. 테스트 실행 결과와 미실행 이유
5. 출시 전 남은 필수 확인
6. commit/push/deploy를 수행하지 않았음

범위 밖 버그가 발견되면 근거와 영향, 출시 차단 여부를 보고한다. 보안 문제를 숨기지 않되 무관한 대규모 수정으로 범위를 확장하지 않는다.

Serena가 제공되는 환경이면 관련 심볼 탐색과 targeted inspection에 활용한다. 사용할 수 없으면 제공된 도구로 필요한 파일만 확인한다.
기존 패턴을 재사용하고, 전체 저장소 반복 읽기나 모든 문서 재생성을 하지 않는다.
우선순위: 정확성 > 보안·개인정보 > 기존 기록·호환성 > 테스트·문서 > 토큰 효율.
